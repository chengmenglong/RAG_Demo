# AI 私有知识库系统执行协议

本文规定后续实现任务的统一执行方式，主要面向上下文较短、规划能力较弱的 Luna 模型。本文使用“必须”“不得”“仅允许”表达强制规则；除非用户明确修改规则，否则执行者不能自行放宽。

## 1. 核心原则

1. 一次只执行一张任务卡。
2. `docs/implementation/EXECUTION_STATE.md` 是任务和阶段状态的唯一来源。
3. 对话历史不是进度证据；仓库文件、实际命令输出、测试结果和本地提交才是证据。
4. 当前任务没有通过完成门时，不得开始下一任务，也不得顺手实现后续功能。
5. 不得把“文件已创建”“代码看起来正确”“测试已编写”写成“测试已通过”。
6. 只修改任务卡授权的范围；发现范围外问题时记录，不顺手修复。
7. Demo、Mock 与真实外部服务验证必须明确区分。

## 2. 治理文件的职责

- `EXECUTION_STATE.md`：唯一状态源，记录当前任务、阶段状态、验证证据和提交 SHA。
- `DECISIONS.md`：记录执行期间新增或变更的技术决定，禁止静默改变架构和契约。
- `FAILURE_LOG.md`：记录失败原文、诊断、尝试和升级信息；它不替代状态文件。
- 当前任务卡：定义目标、非目标、允许范围、步骤和完成门；任务卡本身不得保存动态状态。
- 架构、API、数据契约和验收文档：提供当前任务必须遵守的冻结约束。

当文件间内容冲突时，按以下顺序处理：

1. 用户最新明确指令；
2. 仓库级 `AGENTS.md` 或同类强制说明；
3. 已接受且未被替代的架构/契约决定；
4. 本执行协议；
5. 当前任务卡。

发现冲突后不得自行猜测。应记录冲突，必要时将当前任务标记为 `BLOCKED`。

## 3. 单任务执行规则

任意时刻最多只能有一个任务处于 `IN_PROGRESS`。

开始任务前必须同时满足：

- `EXECUTION_STATE.md` 中没有其他 `IN_PROGRESS` 任务；
- 当前任务状态为 `READY`；
- 所有前置任务均为 `DONE`，或存在明确批准的例外；
- 当前任务卡存在且内容完整；
- 工作树中的已有改动已确认归属，不会被覆盖；
- 当前任务的前置验证通过。

执行者不得：

- 并行处理两张任务卡；
- 在等待测试时切换到另一任务；
- 为“以后可能需要”提前创建空模块；
- 把范围外修复混入当前任务；
- 擅自扩大任务目标以追求一次性完成整个阶段。

如果当前任务暴露出新的必要工作，应新建后续任务卡或记录待办，不得静默扩大当前任务。

## 4. 每次恢复上下文的固定顺序

无论是新会话、模型切换、上下文压缩，还是中断后继续，都必须按以下顺序恢复：

1. 读取用户当前请求和仓库级说明文件。
2. 读取 `docs/implementation/EXECUTION_STATE.md`。
3. 确认 `当前任务` 与任务表中的唯一 `IN_PROGRESS` 行一致。
4. 读取当前任务卡；若当前任务为 `NONE`，只选择状态为 `READY` 且依赖满足的第一张任务卡。
5. 读取任务卡“必读内容”列出的架构、契约和代码文件，不做无边界全仓扫描。
6. 执行以下只读检查：

   ```powershell
   git branch --show-current
   git status --short
   git log -5 --oneline
   ```

7. 查看当前任务已有 diff，确认它们均属于当前任务。
8. 运行任务卡列出的前置验证命令。
9. 在开始修改前，用四句话明确：
   - 本次唯一目标；
   - 本次明确不做的事项；
   - 允许修改的文件范围；
   - 判定完成所需的验证。
10. 将任务状态从 `READY` 更新为 `IN_PROGRESS`，同时更新“当前任务”和尝试次数。

如果第 3、4、7 或 8 步无法确认，不得写代码。先修复状态记录、厘清改动归属或按失败协议升级。

## 5. 标准执行循环

每张任务卡都按同一循环完成：

### 5.1 预检

- 确认分支、工作树和当前任务。
- 确认前置接口、迁移或文件真实存在。
- 运行前置测试，避免把既有失败误算为本任务引入。
- 若预检已有失败，在修改前将其记录到 `FAILURE_LOG.md`。

### 5.2 最小实现

- 严格按任务卡步骤实施。
- 先满足冻结契约，再考虑内部优化。
- 只添加当前行为需要的依赖。
- 新依赖必须有用途、版本理由和锁文件变更。
- 不为通过测试而削弱关键断言或隐藏异常。

### 5.3 局部验证

- 优先运行与改动最接近的单元测试或类型检查。
- 失败时停止扩展功能，进入失败处理。
- 每次修复后重新运行能够复现原错误的最小命令。

### 5.4 完整任务验证

- 运行任务卡列出的全部自动验证命令。
- 执行至少一个正常行为验证和一个负向行为验证。
- 检查日志和响应中没有 API Key、Authorization Header 或其他敏感信息。
- 若更改了数据、API 或状态机契约，确认相应文档和测试同步更新。

### 5.5 Diff 复核

至少执行：

```powershell
git status --short
git diff --check
git diff --stat
git diff
```

复核以下事项：

- 只包含当前任务相关改动；
- 没有意外生成物、真实密钥、数据库文件或上传文件；
- 没有未说明的 `TODO`、`pass`、空实现或永久跳过测试；
- 没有删除用户已有改动；
- 没有顺带重构无关模块。

### 5.6 状态、提交与交接

为避免“提交本身的 SHA 无法预先写进同一个提交”的循环，采用两步本地提交：

1. 将命令、退出码和关键证据写入 `EXECUTION_STATE.md`，提交字段暂写 `CHECKPOINT_PENDING`。
2. 仅在完成门全部通过后，将任务标记为 `DONE`，清除“当前任务”，并把下一项满足依赖的任务改为 `READY`。
3. 仅暂存当前任务的代码、测试、文档和上述状态变更。
4. 创建本地任务 checkpoint commit；测试未通过时不得创建完成点。
5. 运行 `git rev-parse HEAD` 获取任务 checkpoint SHA。
6. 将该 SHA 写回状态文件，并创建一个仅包含该状态写回的本地元数据提交，例如 `chore(state): record Pxx-Txx checkpoint`。状态元数据提交本身的 SHA 不需要递归写入。
7. 若任务明确不要求提交，直接写 `NO_COMMIT（原因）`，跳过第 3–6 步；不能留空。
8. 使用本文规定的固定交接格式汇报。

## 6. 状态转换

允许的任务状态为：

- `NOT_STARTED`：尚未满足依赖或任务卡尚未就绪。
- `READY`：依赖满足，可以开始。
- `IN_PROGRESS`：当前唯一正在执行的任务。
- `BLOCKED`：已经按失败升级规则停止，需要新信息、外部条件或更高能力审查。
- `DONE`：完成门和验证均已通过。
- `SKIPPED`：仅限用户明确取消或已接受决定证明不需要，必须记录原因。

允许的常规转换为：

```text
NOT_STARTED → READY → IN_PROGRESS → DONE
                              └──→ BLOCKED
BLOCKED → READY
NOT_STARTED / READY → SKIPPED（仅在有明确批准时）
```

不得从 `IN_PROGRESS` 直接改回 `NOT_STARTED` 来隐藏失败。解除 `BLOCKED` 时必须在状态文件中记录解除原因。

阶段状态使用同一组状态。阶段状态是任务状态的摘要，必须与本文件内的任务行同步更新：

- 阶段有一个 `IN_PROGRESS` 任务时，阶段为 `IN_PROGRESS`；
- 阶段存在未解除阻塞且没有可继续任务时，阶段为 `BLOCKED`；
- 阶段所有必需任务均为 `DONE`，且阶段门通过后，阶段才为 `DONE`；
- 后续阶段不能因为已建立占位任务就提前标记为 `READY`。

## 7. 完成门

任务只有同时满足以下条件才能标记为 `DONE`：

- 可观察行为已实现；
- 指定测试已实际执行且退出码为 0；
- 至少一个失败或非法输入路径符合契约；
- 相关类型检查、lint 或构建已按任务卡执行；
- `git diff --check` 通过；
- 变更范围仅属于当前任务；
- 状态、决定和失败记录已同步；
- 不存在会阻断后续任务的已知严重问题；
- 已创建本地任务 checkpoint，并完成 SHA 状态写回，或明确记录 `NO_COMMIT` 原因。

以下内容不构成完成证据：

- 只创建了文件；
- 只安装了依赖；
- 只编写了测试但未运行；
- 只得到 HTTP 200，但没有验证业务数据；
- Mock 成功却声称真实 Provider 已验证；
- 仅凭代码阅读判断“应该能运行”。

## 8. 固定交接格式

每次任务结束，无论成功、失败还是阻塞，都必须输出以下结构：

```text
RESULT: PASS | FAIL | BLOCKED
TASK: Pxx-Txx
GOAL: 本任务的一句话目标
FILES_CHANGED:
- 路径：变更作用
COMMANDS_AND_EXIT_CODES:
- 命令：退出码；关键结果
ACCEPTANCE_EVIDENCE:
- 完成门条目：对应证据
DECISIONS:
- 决定编号，或 NONE
FAILURES:
- 失败编号，或 NONE
KNOWN_LIMITATIONS:
- 已知但不属于本任务的问题，或 NONE
COMMIT:
- SHA，或 NO_COMMIT（原因）
NEXT_UNLOCKED_TASK:
- 下一任务 ID，或 NONE
```

交接内容必须与仓库和状态文件一致。不得在交接中把未验证事项写成已完成。

## 10. Git 规则

1. 每次开始前必须检查分支和工作树。
2. 只暂存当前任务相关文件；不得使用会包含未知文件的宽泛暂存方式。
3. 已有未提交改动默认属于用户或其他任务，除非证据表明属于当前任务。
4. 不得使用 `git reset --hard`、`git clean -fd`、强制 checkout 或其他破坏性恢复方式。
5. 不得修改、删除或提交范围外文件来获得“干净工作树”。
6. 本地提交必须在任务验证通过之后创建。
7. 推荐 Conventional Commit，例如 `feat(ingestion): validate uploaded files`。
8. 任务 checkpoint 后允许追加一个只写回该 checkpoint SHA 的状态元数据提交；该提交不能混入代码或下一任务改动。
9. 不得自动 `git push`，不得创建远端分支，除非用户在当前任务中明确授权。
10. 不得自动 rebase、squash、amend 已完成任务或重写历史。
11. 若仓库本来不干净，应精确暂存当前任务文件，并在交接中说明未包含的既有改动。

## 11. 失败升级摘要

详细记录格式见 `FAILURE_LOG.md`。执行时遵守：

- 第一次失败：保存原始错误，提出一个有证据的根因假设并进行最小修复。
- 第二次出现同一错误特征：必须采用不同假设，记录两次差异。
- 同一错误连续两次没有实质进展，或单任务累计三次仍未通过：停止盲目重试，将任务标记为 `BLOCKED` 并升级。
- 升级记录必须说明：最小复现、已排除原因、当前 diff、所需信息以及建议下一步。
- 外部 API、密钥、网络或 Docker 环境不可用时，可完成 Mock/静态验证，但不得把相应现场验证标记为通过。

## 12. 明确禁止事项

- 不得把主要逻辑集中进单个入口文件或页面。
- 不得硬编码 API Key、客户名、固定厂商、模型或绝对运行路径。
- 不得在日志或普通设置 API 中返回敏感密钥。
- 不得伪造测试结果、Citation、页码或外部服务成功记录。
- 不得删除失败测试、放宽关键断言或无条件跳过测试来获得绿色结果。
- 不得用无证据的大重构解决局部问题。
- 不得把未来 OCR、RBAC、Agent、知识图谱等扩展做成当前 MVP 的空壳模块。
- 不得自动提交范围外改动，也不得自动 push。

## 13. 每轮可直接复制给 Luna 的提示词

下面的提示词用于一轮只执行一张任务卡。用户不需要手工替换任务 ID；Luna 必须从状态文件读取。

```text
你现在负责继续实现当前仓库中的 AI 私有知识库系统。本轮只允许完成一张原子任务卡。

严格按以下顺序执行：
1. 完整读取 docs/implementation/EXECUTION_STATE.md。
2. 完整读取 docs/implementation/04_EXECUTION_PROTOCOL.md。
3. 从 NEXT_TASK / 下一候选任务取得唯一任务 ID；确认其状态为 READY，且没有其他 IN_PROGRESS。
4. 打开该任务所属的 docs/implementation/tasks/Pxx.md，只读取并执行对应 Pxx-Txx 小节。
5. 按任务卡要求读取相关架构、API/数据契约和现有代码；不要重新选择技术栈。
6. 修改前先检查 git branch、git status、git log，并用四句话汇报：唯一目标、明确非目标、允许修改范围、完成门。
7. 将该任务改为唯一 IN_PROGRESS，然后只实现此卡；不要提前做下一卡或未来功能。
8. 实际运行卡片中的自动、正常和负向验证，检查退出码、git diff --check 和完整 diff。
9. 只有全部完成门通过才标 DONE；失败按 FAILURE_LOG 规则记录，不能删测试、弱化断言或伪报通过。
10. 更新 EXECUTION_STATE.md 的状态、证据、提交字段和 NEXT_TASK。只精确暂存当前任务文件；可创建本地 checkpoint，但不得 push。
11. 最后严格使用执行协议的固定交接格式。完成一张卡后立即停止，不继续下一张。

除非出现确实需要用户提供密钥、外部环境、权限或产品选择的阻塞，否则不要逐步询问我。Mock、Demo 和真实外部服务结果必须分开陈述。
```

如果 `NEXT_TASK` 为 `NONE`、不是 `READY`、状态表有多个 `IN_PROGRESS`，或任务卡与冻结契约冲突，本轮不得编码；只修复/报告治理冲突并按协议交接。
