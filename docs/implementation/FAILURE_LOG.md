# 失败记录与升级日志

## 1. 用途和边界

本文件保存可复现失败、诊断假设、处理尝试和升级结果，防止 Luna 重复相同动作或把未验证事项写成完成。

本文件不是状态源。记录失败后，必须同时在 `EXECUTION_STATE.md` 中更新尝试次数、关联失败编号以及必要的 `BLOCKED` 状态。

日志应保存关键错误原文，但不得写入 API Key、Authorization Header、密码、完整敏感请求体或客户数据。敏感值使用 `[REDACTED]`。

## 2. 失败分类

每条记录选择一个主分类，必要时增加次分类：

| 分类 | 定义 | 常见例子 |
|---|---|---|
| `IMPLEMENTATION` | 当前实现存在逻辑、类型或资源管理缺陷 | 断言失败、空引用、资源未清理 |
| `CONTRACT` | 模块间字段、状态、错误或语义不一致 | API 字段漂移、页码口径不同 |
| `DEPENDENCY` | 包版本、锁文件、构建工具或运行时不兼容 | 解析器版本冲突、Node/Python 不兼容 |
| `ENVIRONMENT` | 本机权限、缺少可执行程序、端口或文件系统条件 | Docker 未安装、端口占用、权限拒绝 |
| `EXTERNAL` | 网络、第三方 API、密钥、配额或远端服务异常 | 401、429、DNS、Ollama 未运行 |
| `TEST_DEFECT` | 测试夹具或断言与已接受契约冲突 | fixture 错误、测试依赖污染 |
| `DATA` | 输入文件、数据库状态、迁移或编码异常 | 损坏 PDF、重复记录、乱码 |
| `SECURITY` | 密钥泄露、路径穿越、越权或不安全默认值 | 日志打印 Key、文件逃逸存储目录 |

分类不能代替根因。若尚未确定根因，明确写“根因未确认”。

## 3. 尝试和连续失败定义

一次“尝试”必须同时包含：

- 一个明确、可证伪的根因假设；
- 为验证该假设进行的最小改动或诊断；
- 重新运行同一最小复现命令；
- 记录新的结果。

仅重复同一命令、重启终端或无依据改多处代码，不算有效的新尝试。

“同一错误”指以下特征基本一致：

- 同一失败命令；
- 同一异常类型、状态码或失败断言；
- 同一业务步骤；
- 没有出现能够证明问题已向前推进的新结果。

## 4. 固定处理流程

### 第一次失败

1. 停止扩大改动。
2. 保存最小复现命令、退出码和关键错误原文。
3. 判断失败是否在当前任务范围内。
4. 提出一个基于证据的根因假设。
5. 做最小诊断或修复，并重跑同一复现命令。
6. 更新本日志和状态文件中的尝试次数。

### 第二次同类失败

1. 不得重复第一次相同的处理动作。
2. 明确写出第一次假设为何不足。
3. 使用不同的证据来源或不同假设。
4. 检查冻结契约、依赖版本、环境和已有 diff。
5. 再次运行同一最小复现命令。

### 强制升级

满足任一条件时停止盲目重试：

- 同一错误连续两次没有实质进展；
- 单个任务累计三次有效尝试仍未通过；
- 需要用户提供密钥、账号、许可、业务选择或外部资源；
- 继续处理将要求更换已接受架构、破坏数据或修改任务范围外文件；
- 发现安全问题，继续运行可能泄露密钥或损坏数据。

升级动作：

1. 将任务状态改为 `BLOCKED`。
2. 清楚保留当前 diff，不使用破坏性 Git 命令。
3. 写出已排除原因、剩余假设和最小解除条件。
4. 记录需要谁提供什么信息，禁止只写“需要帮助”。
5. 在交接中返回 `RESULT: BLOCKED`。
6. 不开始下一任务，除非状态计划明确存在不依赖该阻塞项的任务并由更高层重新排程。

## 5. 不同失败类型的处理边界

### 实现或契约失败

- 优先缩小到最小单元测试或 API 复现。
- 先核对冻结契约，再决定改生产代码还是测试。
- 不得为绿色测试删除断言、吞异常或返回假成功。

### 依赖失败

- 记录运行时和包管理器版本。
- 先查锁文件和官方兼容范围。
- 更换主要依赖或大版本前必须新增决定记录。
- 不得在业务任务中无边界升级全部包。

### 环境失败

- 把代码缺陷与本机缺失条件分开。
- 能做静态验证时记录为“静态验证通过”，不能写成“实际启动通过”。
- 权限或工具缺失应记录确切命令和解除条件。

### 外部服务失败

- 401/403：检查配置存在性和请求目标，不打印真实密钥。
- 429/超时：验证超时和错误映射，不进行无限重试。
- 无密钥时使用既定 Demo/Mock 契约验证，但把真实 Provider 现场验证保留为未执行。
- 不得把 Mock 输出声称为 OpenAI-compatible 或 Ollama 的真实响应。

### 数据或安全失败

- 首先停止可能继续损坏或泄露数据的流程。
- 不删除原始数据来掩盖错误。
- 使用脱敏副本或最小样本复现。
- 安全问题默认升级，不以“仅 Demo”为理由忽略。

## 8. 失败关闭检查清单

失败只能在原最小复现和相关回归验证都通过后标记为 `RESOLVED`：

- [ ] 原错误的复现命令现在通过
- [ ] 相关回归测试通过
- [ ] 根因而非表面症状已记录
- [ ] 没有弱化测试或吞掉异常
- [ ] 没有泄露敏感信息
- [ ] `EXECUTION_STATE.md` 已同步
- [ ] 修复提交或 `NO_COMMIT` 原因已记录
